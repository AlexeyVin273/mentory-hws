# React Priority Lab

Самостоятельный демонстрационный проект урока 02. React 19.3.1, Vite 8.3.5, JavaScript. Сетевые API, аккаунты и ключи не нужны. Интернет нужен для первой установки пакетов; после этого лаборатория работает локально.

## Запуск

Нужен Node.js **22.12+** (подходит Node.js 24). Откройте терминал именно в этой папке `demo`:

```powershell
npm ci
npm run dev
```

Откройте `http://127.0.0.1:5174`. Порт отличается от проекта первого урока. Если порт занят, остановите свой предыдущий процесс или запустите `npm run dev -- --port 5175`.

Проверка production:

```powershell
npm run build
npm run preview
```

Адрес preview: `http://127.0.0.1:4174`. Завершение сервера — `Ctrl+C`.

## Опыт 1: сравнить поиск

1. Выбрать обычный режим и 80 000 итераций.
2. Быстро набрать `React`, очистить, набрать `CSS`.
3. Записать ощущение ввода и запрос в заголовке списка.
4. Повторить transition и deferred без смены нагрузки.
5. При слабом эффекте выбрать 320 000 или одинаковое CPU throttling в DevTools. Не повышать нагрузку бесконечно.
6. Вернуть нулевую нагрузку. Обсудить, оправдана ли оптимизация для дешёвого списка.

`isPending` описывает transition; `text !== deferredText` показывает отставание значения. Приложение не показывает выдуманные миллисекунды или счётчик «точного числа render». При быстром завершении индикатор может быть незаметен.

## Опыт 2: граница компонентов

Открыть `Results.jsx`. Найти `memo`, сравнить props во время срочного ввода. В своей копии временно убрать обёртку, повторить опыт и вернуть. Не передавать свежий текст input списку отдельным prop.

Нагрузка специально находится в отдельных `CourseCard`. React может управлять работой между компонентами, но один длинный синхронный вызов остаётся блокирующим. `calculateChecksum` использует ограниченный детерминированный цикл и не меняет внешние данные; в реальном каталоге такой код не нужен.

## Опыт 3: чистота

Нажать «Вызвать обе функции дважды». Сравнить строки. Открыть `PurityLab.jsx` и объяснить скрытое состояние замыкания. Это ручной вызов функций в обработчике, а не доказательство количества попыток render React.

## Контрольные сценарии

- Все три режима: `React` → 40 результатов; `CSS` → 40; `zzzz` → 0; очистка → 240.
- Поиск не учитывает регистр и пробелы по краям: ` react ` → 40.
- После завершения обновления заголовок списка соответствует актуальному вводу.
- Смена режима и кнопка сброса очищают поиск — это намеренное поведение.
- Смена нагрузки не очищает поиск, но может сама временно блокировать UI.
- В лаборатории чистоты первая функция возвращает вызовы 1 и 2, вторая — одинаковые приветствия. Повторное нажатие создаёт новый опыт с 1 и 2.
- Управление доступно с клавиатуры; input и оба select имеют подписи. Старый результат обозначен не только цветом, но и текстом статуса.

## Ограничения сравнения

Это лабораторная модель, а не бенчмарк. Количество совпадений влияет на нагрузку. DevTools, StrictMode в development и устройство влияют на наблюдения. Первый render не демонстрирует преимущество отложенного значения: предыдущего списка ещё нет. Здесь нет debounce, fetch, Suspense, Worker или виртуализации. Эти механизмы нельзя считать реализованными по наличию transition.
